Aadhaar-Based Identity Verification Flowchart (ZKP PoC)

Illustrating the client-side and platform-side processing for the "Green Badge" using Aadhaar eKYC.

Phase 1: Client-Side Data Preparation & Proof Generation

1. Input Acquisition & Parsing

User provides their Aadhaar eKYC XML (and share phrase). The client-side tool decrypts and securely parses this XML locally. User also provides their claimed profile name and DoB for the social media platform.

Inputs: Aadhaar eKYC XML (e.g., containing "SINDHURAS", "30-11-2001", Gender "F", Last4 "7439"), Share Phrase, Claimed Profile Name ("SINDHURAS"), Claimed Profile DoB ("30-11-2001"), Social Media Handle ("@SindhuHandle").
Output: Parsed & structured Aadhaar data, UIDAI signature components, user's claimed data.

2. UIDAI Signature Verification (Client-Side)

The client-side tool verifies the UIDAI's digital signature on the parsed eKYC XML data using standard cryptographic libraries (e.g., ECDSA/RSA verification) and UIDAI's public key (extracted from the XML's certificate, chained to a trusted root).

Inputs: Parsed Aadhaar data (specifically the signed portion's hash), UIDAI's signature components, UIDAI's public key.
Process: Standard digital signature verification algorithm.
Output: Boolean (Signature Valid / Invalid). Process halts if invalid.

3. Feature Extraction & Demographic Match

Key demographic features (Name, DoB, Gender, Last4Digits of Aadhaar) are extracted from the now-verified Aadhaar data. These are then compared against the user's claimed profile name and DoB.

Inputs: Verified Aadhaar Name ("SINDHURAS"), DoB ("30-11-2001"), Gender ("F"), Last4 ("7439"). Claimed Profile Name ("SINDHURAS"), DoB ("30-11-2001").
Process: Direct comparison (e.g., `AadhaarName === ClaimedName`).
Output: Boolean (Demographics Match / No Match). Process halts if no match.

4. Nullifier Calculation

A unique nullifier is computed client-side using a ZKP-friendly hash (Poseidon) of stable, verified Aadhaar demographic data (Name, DoB, Gender, Last 4 Digits), the social media handle, and a system-specific salt. This prevents double-registration for the same identity.

Inputs: Verified Aadhaar Name ("SINDHURAS"), DoB ("30-11-2001"), Gender ("F"), Last4 ("7439"), SocialMediaHandle ("@SindhuHandle"), SALT.
Process: `Nullifier = PoseidonHash(Name, DoB, Gender, Last4, Handle, SALT)`.
Output: `ComputedNullifier` (e.g., "999988887...").

5. Witness & Public Input Preparation

All private inputs (verified Aadhaar data, user claims, UIDAI signature components) and public inputs (claimed handle, computed nullifier, commitments like hash of Aadhaar demographics) are assembled for the ZKP circuit.

Output: Structured `input.json` for the ZKP witness calculator.

6. ZKP Proof Generation

The client-side tool uses the prepared witness, the Proving Key (specific to the Aadhaar verification Circom circuit), and standard ZKP libraries (e.g., `snarkjs` with Groth16) to generate the Zero-Knowledge Proof (`π`) and the final public outputs.

Inputs: Witness (`.wtns`), Proving Key (`.zkey`).
Process: Groth16 `prove` algorithm.
Output: `ZKProof (π)`, `PublicOutputs` (containing nullifier, commitments, claimed handle, etc.).

Data Packet Sent to Platform: { ZKProof (`π`), PublicOutputs (incl. Nullifier, Handle, Commitments), EntityType }

Phase 2: Platform-Side Verification & Decision Making

7. Receive Submission Package

The platform's secure API endpoint receives the ZKProof, PublicOutputs, and EntityType from the client. Initial validation of package format and completeness is performed.

Input: Data Packet from Client.

8. ZKP Proof Verification

The platform retrieves the Verification Key (VK) corresponding to the Aadhaar verification circuit. It then runs the standard Groth16 `verify` algorithm using the VK, the submitted ZKProof, and the PublicOutputs.

Inputs: ZKProof (`π`), PublicOutputs, Verification Key (`.json`).
Process: Groth16 `verify` algorithm.
Output: Boolean (Proof Valid / Invalid).

Decision: Is Proof Valid?

YES

9. Nullifier Uniqueness Check

If the proof is valid, the platform extracts the `Nullifier` from the PublicOutputs. It queries its secure nullifier database to check if this nullifier has already been recorded for this identity type.

Input: `Nullifier`.
Process: Database lookup.
Output: Boolean (Nullifier Unique / Already Exists).

Decision: Is Nullifier Unique?

YES

10. Record Nullifier & Issue Badge

If unique, the nullifier is recorded. The "Green Badge" is issued to the user's social media handle. User is notified.

NO

Application rejected (Nullifier already used). User is notified.
